# Обоснование конфигурации инфраструктуры

## Выбор ресурсов и параметров

### Виртуальные машины

| VM | CPU | RAM | Назначение |
|---|---|---|---|
| Airflow | 2 cores | 4 GB | Оркестрация ETL-пайплайнов. Нетребователен к ресурсам — управляет задачами, не обрабатывает данные |
| MinIO | 2 cores | 8 GB | S3-совместимое хранилище. Больше памяти для кэширования операций чтения/записи |
| Trino + Metabase | 4 cores | 16 GB | Query-движок для аналитических запросов к сотням ТБ данных. Требует больше CPU и RAM |
| DataHub | 4 cores | 16 GB | Каталог данных с ElasticSearch внутри. ElasticSearch требователен к памяти |

Все VM используют `core_fraction = 20` — прерываемая нагрузка на CPU. Это снижает стоимость для dev/staging окружения.

### Диски

| Диск | Размер | Тип | Назначение |
|---|---|---|---|
| airflow-data-disk | 30 GB | network-ssd | Логи и метаданные Airflow. SSD для быстрого доступа |
| minio-data-disk | 100 GB | network-hdd | Данные хранилища. HDD дешевле для больших объёмов |
| Boot диски | 20-30 GB | network-ssd | ОС и приложения |

MinIO использует `network-hdd` — объектное хранилище не требует низкой латентности SSD, зато выигрывает в стоимости на больших объёмах.

### Сеть

Все VM находятся в одной VPC и подсети `10.0.0.0/24`. Это обеспечивает:
- низкую латентность между сервисами (внутренняя сеть)
- изоляцию от внешнего трафика

NAT включён для всех VM — необходим для:
- доступа к UI сервисов извне
- скачивания Docker образов и пакетов при настройке

Security Group разрешает только конкретные порты каждого сервиса, блокируя всё остальное.

## Что управляется Terraform, что вручную

### Terraform (автоматически)
- VPC сеть и подсеть
- Security Groups и правила
- Виртуальные машины (EC2-эквивалент)
- Диски и их подключение к VM
- NAT и сетевые интерфейсы

### Вручную (после terraform apply)
- Установка Docker на каждую VM
- Запуск Docker Compose с сервисами (Airflow, MinIO, Trino, Metabase, DataHub)
- Настройка подключений между сервисами
- Конфигурация Airflow пайплайнов
- Настройка DataHub коннекторов

## Декларативный подход и IaC

### Почему декларативный подход

Terraform использует декларативный подход — описываем **что** должно быть, а не **как** создавать.

```hcl
# Декларативно: описываем желаемое состояние
resource "yandex_compute_instance" "airflow" {
  resources {
    cores  = 2
    memory = 4
  }
}
```

Альтернатива — императивный скрипт:
```bash
# Императивно: описываем каждый шаг
yc compute instance create ...
if [ $? -eq 0 ]; then
  yc compute disk attach ...
fi
```

Декларативный подход лучше потому что:
- Terraform сам определяет порядок создания ресурсов
- Повторный запуск безопасен (идемпотентен)
- Легко читать и понимать текущее состояние

### Воспроизводимость

IaC обеспечивает идентичные окружения:

```
terraform apply → dev окружение
terraform apply → staging окружение  (те же параметры)
terraform apply → prod окружение      (те же параметры)
```

Без IaC каждое окружение настраивается вручную → расхождения конфигураций → "работает на dev, не работает на prod".

### Масштабируемость

Добавление нового сервиса (например, выделенный Nessie сервер) — это добавление нового блока `resource` в `main.tf`:

```hcl
resource "yandex_compute_instance" "nessie" {
  ...
}
```

Один `terraform apply` — и инфраструктура обновлена. Не нужно помнить какие команды выполнять вручную.

### Версионирование

Terraform конфиги хранятся в Git. Это даёт:
- историю изменений инфраструктуры
- возможность откатиться к предыдущей конфигурации
- code review изменений инфраструктуры как обычного кода
